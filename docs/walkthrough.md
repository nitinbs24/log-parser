# Part 0: Concepts to read first (30–60 min)

Read these before touching code. They make every later step make sense.

1. **Guide §1** (the task) and **§3** (metrics). Be able to explain:
   - what a template is and what a variable is,
   - why PA (exact match) is your headline metric,
   - why GA can look good even when templates are wrong.
2. **LLMParser paper abstract and method section** (arXiv:2404.18001). It is your closest prior work. Note that they trained per system. You will train across systems and test on **unseen** systems.
3. **LoRA in one paragraph.** You freeze the base weights and train two small matrices (rank `r`) per targeted layer. The adapter is tens of MB. `alpha / r` scales how strongly the adapter affects the output. **QLoRA** keeps the frozen base in 4-bit to save VRAM; the adapter itself stays in higher precision.
4. **Completion-only loss.** The training text is `prompt + answer`. You want the model graded only on the answer (the template). Otherwise the long prompt dominates the loss.

**Learn check:** Why does a random line-level train/test split give fake accuracy on logs? (Answer: thousands of lines share one template, so the test template is already in train.)

## Step 2.3: Write `src/prepare_data.py`

Structure (write each function and test it before the next):

1. `load_system(name) -> DataFrame` with columns `system, content, template`.
2. `normalize(template)` calls the vendored `post_process`. Apply it to **targets** so the model learns the same normalised style the evaluator expects.
3. `dedupe` on `(system, content)`.
4. `split_systems`: held-out systems go to `test_heldout.jsonl` untouched except for dedupe.
5. For the remaining 12 systems, do the **template-disjoint split**: shuffle the unique templates of each system with the seed, send 70% to train-candidates and 30% to `test_template_disjoint`. Then carve **validation** from the train-candidate templates, again template-disjoint.
6. Cap at `per_template_cap` lines per template in train.
7. Drop lines over `max_tokens`. Approximate by whitespace token count first; refine with the real tokenizer later.
8. Write chat-format JSONL:

```python
SYSTEM_PROMPT = ("You are a log parser. Replace every variable in the log message "
                 "with <*>. Output only the template.")

def to_example(system, content, template):
    return {"messages": [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": f"System: {system}\nLog: {content}"},
        {"role": "assistant", "content": template},
    ]}
```

Put `SYSTEM_PROMPT` and the prompt builder in one shared module (e.g. `src/prompt.py`). **Training, prediction, baselines, and Phase B must all import the same function**, or your comparison is invalid (guide §10).

9. **The leakage guard.** At the end of the script:

```python
train_templates = {ex["messages"][-1]["content"] for ex in train}
for name, split in test_splits.items():
    leaked = {t for t in split_templates(name)} & train_templates
    assert not leaked, f"{name}: {len(leaked)} templates also in train, e.g. {list(leaked)[:3]}"
```

Note one subtlety: two different systems can share a template string (e.g. a very generic one). Decide deliberately whether that counts as leakage for the cross-system split, and write the decision in the data card. If it happens, either drop those lines from train or drop them from the held-out set. Don't ignore it.

10. Generate `reports/data_card.md` from the script: lines and templates per system and split, token-length distribution, and the top-10 template frequencies.

## Step 2.4: Test it

Write `tests/test_prepare_data.py` with at least:


## Step 2.5 (parallel, any time): Handcrafted benchmark (T1b)

This is the part only you can do, and it is the most valuable for the real-world goal.

1. Collect 5–10 real lines from each of: Kafka, Redis, OpenSearch, Docker, Kubernetes (kubelet), PostgreSQL, Nginx. **Remove secrets, tokens, internal hostnames and IPs you don't want in a public repo** before saving.
2. Strip the header the same way Loghub does (use only the message `Content`).
3. Label each template by hand. Follow Loghub's conventions by looking at how similar lines are labelled in the Loghub CSVs. When in doubt: numbers, IDs, IPs, paths, hostnames, durations and user-specific strings are variables; fixed words and keywords like `ERROR`/`INFO` in the message body are usually constants.
4. Make sure every edge-case category appears at least twice: multi-variable, paths/URLs, JSON-in-log, stack-trace header, constant numbers (`HTTP/1.1`), no-variable lines.
5. Save as `data/handcrafted/benchmark.csv` with columns `system,content,gold`.

Do not look at this set while tuning. It is your out-of-distribution check.

**Done when**
- [ ] `make data` reproduces identical files twice.
- [ ] The leakage assertion passes, and you have seen it fail on a fake leaky split.
- [ ] `reports/data_card.md` exists and you've read it.
- [ ] You eyeballed 50 pairs and fixed any issues.
- [ ] `benchmark.csv` has ≥30 labelled lines covering every edge-case category.

**Learn:** Explain to yourself the difference between the *cross-system* split (can it handle a system it has never seen?) and the *template-disjoint* split (can it handle a new event type in a known system?). They test different failure modes.

# Part 3: Evaluation and baselines (Tasks T2, T3, T4)

Build the scoring and inference **before** training. Then you know the harness is correct before you spend GPU hours.

## Step 3.1: `src/evaluate.py` (T2)

Goal: `python -m src.evaluate --pred predictions.csv --out results/<model>/<split>.json` → GA, FGA, PA, FTA per system plus the average.

1. Read the vendored evaluator. Find the function that takes a structured CSV with `Content`, `EventTemplate` (gold) and a prediction column, and returns GA/PA/FGA/FTA. **⚠ verify** its input format. You may need to write the predictions in the shape it expects (e.g. a "parsed" CSV with `EventTemplate` as the predicted one).
2. Apply the same `post_process` to gold and predictions before scoring.
3. Write results per system and the macro-average to JSON.

**Sanity check first:** feed gold as predictions. Every metric must be 1.0. Put this in a test:

```python
def test_gold_scores_perfect():
    ...  # PA == 1.0 and GA == 1.0 on a small sample
```

Then feed a fake model that outputs `<*>` for everything. PA should be very low and GA very low (everything lands in one group). If the numbers are not what you expect, fix this **now**; every later conclusion rests on it.

## Step 3.2: Drain baseline, B0 (T2)

`src/baselines/drain_baseline.py`: run `logparser3`'s Drain on each test split, then score with the same `evaluate.py`.

```python
# ⚠ verify against the logparser3 docs: import path and args
from logparser.Drain import LogParser
parser = LogParser(log_format="<Content>", indir=indir, outdir=outdir,
                   depth=4, st=0.5, rex=[])
parser.parse("systemX.log")
```

Notes:
- Drain's `log_format="<Content>"` works because you feed it `Content` only, one line per row. You'll write each split to a temp `.log` file.
- Run Drain **per system**, not on mixed systems. Drain is a per-system parser.
- Use default parameters first. Optionally add a tuned run (with per-system regexes from the Loghub benchmark settings) and report both. A fair baseline is the point.

**Learn:** Drain builds a fixed-depth prefix tree on token counts and leading tokens, and merges lines whose similarity exceeds `st`. That's why it groups well (high GA) but writes poor templates (low PA): it never reads meaning, only token overlap.

## Step 3.3: `src/prompt.py` and `src/predict.py` (T3)

Design rule: `parse_lines` is the **only** function Phase B will call, so keep it independent of splits and evaluators.

```python
# src/predict.py (outline)
def build_messages(system, line): ...          # imports the shared prompt
def clean(raw: str) -> str:                    # first line, strip quotes/backticks
    ...
def parse_lines(lines: list[str], system: str | None = None, *,
                backend: str = "vllm", model: str = ..., adapter: str | None = None,
                ) -> list[str]:
    msgs = [build_messages(system, l) for l in lines]
    if backend == "vllm":   raw = _generate_vllm(msgs, model, adapter)
    elif backend == "ollama": raw = _generate_ollama(msgs, model)
    else: raise ValueError(backend)
    out = [clean(r) for r in raw]
    assert len(out) == len(lines)
    return out
```

**vLLM backend (⚠ verify the API):**

```python
from vllm import LLM, SamplingParams
from vllm.lora.request import LoRARequest
llm = LLM(model, enable_lora=adapter is not None, dtype="half", max_model_len=1024)
sp = SamplingParams(temperature=0, max_tokens=128)
req = LoRARequest("logparser", 1, adapter) if adapter else None
outs = llm.chat(msgs, sp, lora_request=req)    # or build prompts with the tokenizer and use generate()
raw = [o.outputs[0].text for o in outs]
```

**Ollama backend:** POST to `http://localhost:11434/api/chat` with `{"model": ..., "messages": [...], "stream": false, "options": {"temperature": 0}}` and read `message.content`. Use a thread pool of a few workers; CPU inference is slow, so don't flood it.

The CLI part reads a split JSONL, calls `parse_lines`, and writes `system, content, gold, pred` CSV. It also prints how many outputs `clean()` had to change. **That count for the base model is a finding.**

Two details that bite:
- **Qwen3 thinking mode.** Use the `Instruct-2507` model. If you see `<think>` in outputs, you're on the wrong variant or template.
- **Same prompt everywhere.** `build_messages` is the single source. Never copy the prompt string.

**Test without a GPU:** write a stub backend (returns the content unchanged) and test that `parse_lines` preserves length and order. Then run the real vLLM backend on 200 lines on the T4 and the Ollama backend on one line locally.

## Step 3.4: Base model baselines B1 and B2 (T4)

- **B1 zero-shot:** the base model, your exact prompt.
- **B2 few-shot:** the same prompt plus 5 example `(log → template)` pairs as earlier chat turns. Pick examples **from training systems only**, and use the same 5 for every test line (or fixed per system, from a different system if the test one is held out).

Run both on the held-out, template-disjoint and handcrafted sets, score them, and save to `results/`.

Read 20 of the base model's outputs. You'll likely see exactly what guide §1 predicts: placeholders like `{id}`, chatty text, un-replaced IDs. Save a few bad examples for the report.

**Done when (Checkpoint 1)**
- [ ] Gold-as-prediction gives PA = 1.0; all-`<*>` gives a very low score.
- [ ] B0, B1, B2 results exist for held-out, template-disjoint, and handcrafted sets, in the same format.
- [ ] `parse_lines` works through both backends on a small sample.
- [ ] The base model's "cleanup needed" rate is recorded.
- [ ] The numbers look plausible: Drain PA low-ish, base zero-shot worse than few-shot. If not, stop and debug before training.

**Learn:** Why is B2 (few-shot) the most important baseline? A reviewer's first question is "why not just prompt it?" If you can't beat few-shot, fine-tuning isn't justified.

## Step 4.2: `src/train.py` (T5)

Build it in this order, running a tiny test after each stage:

**Stage 1: load and wrap.**

```python
from unsloth import FastLanguageModel
model, tok = FastLanguageModel.from_pretrained(cfg["model"], max_seq_length=cfg["max_seq_length"], load_in_4bit=True)
model = FastLanguageModel.get_peft_model(
    model, r=cfg["lora"]["r"], lora_alpha=cfg["lora"]["alpha"],
    lora_dropout=cfg["lora"]["dropout"], target_modules=cfg["lora"]["target_modules"],
    bias="none", use_gradient_checkpointing="unsloth", random_state=cfg["train"]["seed"])
model.print_trainable_parameters()   # note the % trainable for your report
```

**Stage 2: data → text.** Render each example with the chat template:

```python
def fmt(ex): return {"text": tok.apply_chat_template(ex["messages"], tokenize=False)}
ds = load_dataset("json", data_files={"train": ..., "val": ...}).map(fmt)
```

**Stage 3: trainer with response-only loss.**

```python
from trl import SFTTrainer, SFTConfig
from unsloth.chat_templates import train_on_responses_only
trainer = SFTTrainer(model=model, processing_class=tok, train_dataset=ds["train"],
                     eval_dataset=ds["val"], args=SFTConfig(...))   # ⚠ arg names differ across TRL versions
trainer = train_on_responses_only(
    trainer,
    instruction_part="<|im_start|>user\n",
    response_part="<|im_start|>assistant\n")   # Qwen's template markers
```

**Check the masking.** Decode one batch's labels where they are not `-100`:

```python
b = trainer.train_dataset[0]
labels = [t for t in b["labels"] if t != -100]
print(tok.decode(labels))     # must be ONLY the template (plus the end token), not the prompt
```

If the prompt shows up, your `instruction_part`/`response_part` strings don't match the template. Fix this before any real run.

**Stage 4: PA callback.** Write a `TrainerCallback` that on each evaluation step generates for ~200 validation lines (greedy), applies `clean()` and `post_process`, and logs `val_pa` to W&B. Use the model in `for_inference` mode inside the callback and switch back afterwards. (Simplest correct approach: HF `generate` in batches. vLLM inside a training process fights for VRAM.)

Then set early stopping on `val_pa` (`metric_for_best_model="val_pa"`, `greater_is_better=True`, `load_best_model_at_end=True`). **⚠ verify:** custom metrics from a callback may need to be written into the evaluation logs so the Trainer can see them. If that's awkward, an alternative is a callback that tracks the best `val_pa` and saves that checkpoint itself.

**Stage 5: W&B and resume.** `report_to="wandb"`, log the whole config (`wandb.config.update(cfg)`), log `torch.cuda.max_memory_allocated()` at the end. Use `save_steps=50`, `output_dir` under `outputs/`, and `trainer.train(resume_from_checkpoint=True)` guarded so it only resumes if a checkpoint exists.

**Smoke run:** 20 steps on 100 examples.

```bash
python -m src.train --config configs/smoke.yaml
```

**Learn:** Why early-stop on val PA instead of val loss? Loss measures per-token probability; PA measures exact-string correctness. A model can keep lowering loss while exact match plateaus.

## Step 4.4: The sweep (T7)

Do **one axis at a time** from the defaults (~10 runs), not the 54-run grid:

| Axis | Values | Runs |
|---|---|---|
| Rank | 8, 32 (16 is the default) | 2 |
| LR | 1e-4, 5e-4 | 2 |
| Epochs | 1, 5 | 2 |
| Target modules | `q,v` vs all linear | 1 |
| `System:` line in prompt | on vs off | 1 |

Rules:
- Compare on **validation PA only**. Never look at the held-out systems during the sweep.
- Keep `seed: 42` fixed so differences come from the changed axis.
- Write one config file per run (or use a W&B sweep with `method: grid` over the single axis). Name runs `r8`, `lr1e-4` and so on.
- Then combine the best value per axis in one confirmation run (`configs/best.yaml`) and check it actually beats the default. Axes can interact.

Export the W&B table to `reports/sweep.md` with a short paragraph on what mattered and what didn't.

**Done when**
- [ ] ~10 sweep runs plus 1 confirmation run are logged in W&B.
- [ ] `configs/best.yaml` beats the default on validation PA.
- [ ] `reports/sweep.md` says what you learned.
- [ ] You never touched the held-out systems during the sweep.

# Part 5: Final evaluation and analysis (Tasks T8, T9, T10)

# Part 7: Phase B, the hybrid pipeline (Tasks B1–B7)

**Rules for Phase B:** it lives in `src/pipeline/`; it calls the model only via `predict.parse_lines`; it must not change any Phase A file or result. Its job is to make parsing practical on millions of real lines.

The big idea: lines of the same event share a template. Calling an LLM per line is wasteful. Instead, group lines cheaply (Drain), ask the LLM about **2–3 samples per group**, check the answer against **every** line in the group, and cache what you learn.

## Step 7.1: Pre-parser (B1)

`src/pipeline/preparse.py`. The model was trained on `Content` (message only), so real logs must be reduced to that form.

For each format you care about, write a small header-stripper:

| Format | Typical header | Notes |
|---|---|---|
| Kafka (log4j) | `[2024-05-01 10:00:00,123] INFO ` … `(kafka.server.X)` | Message is between; trailing `(logger)` is part of the header |
| Kubernetes (kubelet) | `I0501 10:00:00.123456 1234 file.go:123] message` | klog format |
| Nginx access | `ip - - [time] "GET /x HTTP/1.1" 200 123 "ref" "ua"` | Decide: the whole line is the message, or strip ip/time. Document it |
| PostgreSQL | `2024-05-01 10:00:00.123 UTC [123] LOG:  message` | |
| Redis | `1234:M 01 May 2024 10:00:00.123 * message` | |
| OpenSearch | `[2024-05-01T10:00:00,123][INFO ][o.o.n.Node] [node] message` | |

Plus two generic steps:
- **JSON logs:** if a line parses as JSON, pull out the message field (`msg`, `message`, `log`, …); keep the other fields as the header.
- **Multi-line folding:** a line that does not start with the format's timestamp pattern is a continuation (stack trace). Attach it to the previous entry. For parsing, use only the first line (the exception header) as the message; keep the rest as an attachment.

Unknown format → pass the whole line through as the message. **Never drop a line.**

Test with a fixture of ≥10 real lines per format (`tests/fixtures/`), asserting the exact extracted message.

## Step 7.2: Group and sample (B2)

`src/pipeline/group.py`.

- Use Drain for grouping. For an in-memory API, the `drain3` package (`TemplateMiner.add_log_message`) is simpler than `logparser3`'s file-based interface. **⚠ verify** and note that you're using a different Drain implementation than the Phase A baseline; say so in the docs.
- For each group, choose 2–3 sample lines (e.g. the shortest, a middle one, and the longest, so variable-heavy lines are represented).
- Call `parse_lines(samples, system=...)` once for the whole batch of samples (batching matters for throughput).
- If the sample templates differ, choose one by a documented, deterministic rule (e.g. most frequent, ties → fewest `<*>`... decide and write it down), then rely on Step 7.3 to catch a bad pick.
- Count LLM calls. You will report **LLM calls per 1M lines**.

## Step 7.3: Regex validation and fallback (B3)

`src/pipeline/validate.py`. Turn a template into a regex and test it on all lines of the group:

```python
import re
def template_to_regex(t: str) -> re.Pattern:
    parts = [re.escape(p) for p in t.split("<*>")]
    return re.compile("^" + "(.+?)".join(parts) + "$")
```

Lines that match keep the template. Lines that don't are re-parsed individually via `parse_lines`. Lines that still fail are flagged `unparsed`; never silently assign a wrong template.

Tests to write: templates with regex-special characters (`[ ] ( ) . * +`), a deliberately wrong template (the fallback must fire), and a template with no `<*>`.

**Learn:** the check proves the template *covers* the lines. It cannot prove it is the *best* template (an over-general `<*> <*> <*>` matches everything). That's a real limitation. Consider a rule that rejects templates with too few constant tokens and write down what you chose.

## Step 7.4: Template cache (B4)

`src/pipeline/cache.py` with a deliberately tiny interface: `get(key)` and `put(key, template)`. Start with a JSONL or SQLite file. This exact interface becomes Redis in Phase C.

The design question is the **key**. Options: the raw message (hit rate ≈ only exact duplicates), or a masked shape (digits → `0`, hex/UUIDs → `H`). Try both on a real file and compare hit rate. Pick the one that gives a high hit rate without wrong merges.

Test: running the same file twice makes ~0 LLM calls on the second run.

# Appendix A: Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `bf16 is not supported` / dtype crash | Copied an A100 config | `fp16: true`, `bf16: false` |
| Training text includes the prompt in the loss | `instruction_part`/`response_part` don't match the template | Print the decoded labels (Step 4.2) and copy the exact markers from `tok.chat_template` |
| Outputs contain `<think>` | Wrong Qwen3 variant | Use `Instruct-2507` or disable thinking in the template |
| Fine-tuned PA ≈ base PA | Prompt differs between train and eval, or masking is wrong | Diff the rendered prompts; check masking |
| PA suspiciously high (>98%) | Template leakage | Re-check the leakage assert; check shared-template strings across systems |
| Run vanished after a disconnect | Output wasn't on Drive | Make sure `outputs/` is the Drive symlink |
| vLLM out of memory with training open | Both on one GPU | Run inference in a separate session |
| `parse_lines` returns shorter list | Model produced empty output and a filter dropped it | Never filter; return `""` and let validation flag it |
| Drain numbers wildly different from papers | Different benchmark or settings | Papers use Loghub-2.0 with tuned settings; yours is Loghub-2k with defaults. Don't compare directly |

# Appendix B: Concepts glossary

- **Template / variable:** the fixed text vs the changing parts of a log line.
- **GA / FGA / PA / FTA:** grouping accuracy (message level), F1 of grouping accuracy (template level), parsing accuracy (exact-match, message level, your headline), F1 of template accuracy (strictest).
- **LoRA / QLoRA:** small trainable low-rank adapters on a frozen base; QLoRA keeps the base in 4-bit.
- **Rank `r`, alpha:** adapter capacity and its scaling (`alpha / r`).
- **Completion-only loss:** compute loss only on the assistant's answer tokens.
- **Template-disjoint split:** train and test share no template strings.
- **Cross-system generalisation:** test on systems never seen in training.
- **GGUF / Q4_K_M:** llama.cpp model format / a 4-bit quantisation scheme.
- **Multi-LoRA serving:** one base model, several adapters selected per request.
